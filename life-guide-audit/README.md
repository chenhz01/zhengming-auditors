# LGA — 生活指南可执行性审计器 v1.0

第九件突破件 · 抖音《当代年轻人的齐民要术》(#生活指南 #github #开源项目)
对应 skill：`zhengming-douyin-learn-breakthrough` §S 七流程

---

## 1. 它解决什么

这个赛道（GitHub 上中文的「年轻人生活 / 生存 / 搞钱指南」）所有人都在回答
**「该怎么做」**，没有一个人回答 **「我做对了没有，这条建议还鲜不鲜」**。

LGA 把后者变成可跑的度量。两个模式：

| 模式 | 干什么 | 为什么存在 |
|---|---|---|
| `list-verify` | 二手清单逐条核真（路径、星数、归档、最近 push） | 治「引用未核实的中间物」这个病 |
| `audit` | 单仓库 Markdown 条目级审计 | 把「指南能不能照着做」变成数字 |

---

## 2. 安装与运行

依赖：Python 3.10+、已授权的 `gh` CLI（凭据走 `gh`，代码里不落 token）。

```bash
# 自检（36 项，含 8 项真数据断言）
python verify.py

# 清单核真：给一份二手清单，逐条验
python lga_cli.py list-verify --input fixtures_good.json     # 全对 -> 退出 0
python lga_cli.py list-verify --input fixtures_bad.json      # 有错 -> 退出 2

# 单仓库审计
python lga_cli.py audit --repo SurviveSJTU/SurviveSJTUManual --max-files 10

# 批量
python lga_cli.py batch --repos "a/b,c/d,e/f" --max-files 10 --json > out.json
```

### 退出码

| 码 | `audit` | `list-verify` |
|---|---|---|
| 0 | `ok` / `mixed` / `caution`（结论可用） | `suspect == 0`（清单全对） |
| 2 | `no_evidence` / `uninformative` / `degenerate` | `suspect > 0`（抓到存疑条目） |

> **两种模式的 `mixed` 语义相反，所以退出码必须分开算。**
> 这是 v1.0 第一版的 bug：共用一套码，导致「核真抓到 3 条错路径」静默退出 0。
> 见 §7 自查记录。

## 3. 度量口径

| 指标 | 定义 | 分母 |
|---|---|---|
| `actionability` | 含动作动词 **且** 有对象 | 未勾选条目（advice） |
| `closure_rate` | 可执行 **且** 含判据信号 | 可执行条目 |
| `verdict_gap` | 1 − closure_rate（可执行却没说「做到什么算对」） | — |
| `freshness_ratio` | 含外部事实（链接/价格/政策/版本）的 **md 文件占比** | 扫描到的 md 文件 |
| `n_meta` | 已勾选 `- [x]` 条目（作者事记，不计入分母） | 全部条目 |

**已勾选复选框要单独剔除**：`- [x] 增加新版序言和声明` 是更新日志，不是给读者的建议。
第一版没剔，结果 SurviveSJTUManual 的可执行率被压到 8.0%，纯属污染。

**保鲜度按文件算，不按条目算**：链接和价格多写在正文段落里，不在列表项里。
第一版按条目查，所有仓库 `freshness_ratio` 恒为 0.0 —— 一个漂亮的假数字。

## 4. 真数据（2026-09-27 实跑，8 个仓库）

| 仓库 | md | 条目 | 可执行率 | 闭环率 | 保鲜风险 | 结论 |
|---|---|---|---|---|---|---|
| SurviveSJTU/SurviveSJTUManual | 10/10 | 206 | 6.9% | 14.3% | 100% | caution |
| QSCTech/zju-icicles | 10/10 | 373 | 1.9% | 42.9% | 70% | mixed |
| geekan/HowToLiveLonger | 2/2 | 445 | 4.3% | 52.6% | 100% | ok |
| Vijin0410/youth-rescue | 1/1 | 3 | 0.0% | 0.0% | 100% | uninformative |
| dowithless/how-to-make-money | 10/10 | 392 | 14.5% | 15.8% | 100% | caution |
| fzxlyd/ai-money-lab | 1/1 | 59 | 6.8% | 0.0% | 100% | caution |
| IanCao/caileme | 10/10 | 181 | 9.9% | 0.0% | 90% | caution |
| Knowckx/awesome-run | 2/2 | 34 | 29.4% | 30.0% | 100% | mixed |

**读法**：可执行率低 ≠ 指南没用。它说明**这些仓库绝大多数条目是陈述、引用、导航，
不是可照做的动作**。真正给了「动作 + 判据」的只有 `HowToLiveLonger`（52.6%）一个过半。

### 样本偏差声明（RA-5，硬交付项）

- 每仓最多扫 **10 个 md**，`HowToLiveLonger` 与 `Knowckx/awesome-run` 全仓只有 2 个 md。
- 启发式词典（动作动词表、判据正则）**未标定**，是工程取值。
- 它度量 **「文本像不像可执行」**，不度量 **「这条建议对不对」**。两者别混用。
- `futongxu9-maker/life-guide`、`lsdsjy/tangping-cities-deck` 取到 `no_evidence`：
  它们是**纯静态 HTML 站，根本没有 Markdown**——不是「可审查的指南文本」。
  这本身是赛道事实：一半内容是成品网页，改了个字你自己都看不见。

## 5. 踩到的坑（v1.0 自检当场抓出的 4 个）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `list-verify` 崩溃 AttributeError | 子解析器没定义 `--json`，`main()` 却读了 `a.json` | 补 `--json`；同类 bug `audit` 子命令也有，一起补 |
| 2 | 围栏写在列表项里（`- ```python`）会吞掉后面所有条目 | 判围栏只看行首，没剥列表前缀 | 判定时先剥掉列表前缀再看 |
| 3 | 「核真抓到 3 条错路径」退出 0 | 两种模式共用退出码，`list-verify` 的 `mixed` 被当成「结论可用」 | 拆出 `list_verify_exit_code()` |
| 4 | 所有仓库取树 404、审计全空 | ① 默认分支是 master 时裸 `git/trees` 404，须显式带分支；② `gh api -f k=v` 对 `git/trees` 不生效，须拼查询串 | 分支回退链 + 查询串拼参 |

第 4 条的两个子坑，任意一个都会让审计**静默返回空结果且不报错**——比报错危险得多。

---

## 6. 已知限制

- 只对 **Markdown** 有效。静态 HTML 站（赛道里的一部分）直接 `no_evidence`。
- 中文分词很糙：靠动词表 + 正则，遇生僻动词会漏判。
- 不联网判断「链接还活不活」：只识别文件里**有**外部事实，不验证**有效性**。
- 不做跨仓库的去重：同一个建议在两个仓里出现，会被算两份。

## 7. 自查记录：三批，来源不同，别混为一谈

### 第一批 —— 开发中被自检抓到的 3 处

**注意：这 3 处在写工具阶段就被抓出来了，不是交付后回审抓的。** 写清楚是为了
让下面的第二批保持可比——两批处理方式不同，别都记成"事后回审的功劳"。
这 3 条都是**口径错、静默通过**一类；⑥ 那张表记的是**直接崩溃或静默返回空**的另一类，
两者口径不同，别混着数。

1. `freshness_ratio` 恒为 0.0 —— **一个漂亮的假数字**，因为测错了对象（按条目而非按文件）。
   真数据一跑就露馅（全 8 仓都是 0.0%）。已改为按文件统计；断言锁在 fixture 上
   （`== 0.25`），真数据上锁的是「按文件算」这条口径。
2. `n_meta` 未剔除 —— 可执行率被更新日志压平（SurviveSJTUManual 一度显到 8.0%）。已剔除并补 3 条断言。
3. 两种模式 `mixed` 语义相反却共用退出码 —— 核真失败静默退出 0。已拆函数并补断言。

### 第二批 —— 真正交付后回审抓到的 1 处

**手册里写的「实扫 2183 条条目」是错的，实际 1693。**
数字凭印象写进交付物，没跟 `audit_real.json` 加总对账。已按数据改回 1693，
并补了一句"每行都能从 audit_real.json 重新加总得到"。

**这才是真正的回审该抓的东西**：工具跑得再绿，交付物里的一个手写数字照样能错。
已写脚本把 HTML 表格的每个百分号、每个条目数、每个 `x/y` 跟 JSON 逐格对账，
结果**全部一致**（对完才发现 KPI 区的总量是手写的、没对过）。

可复现的对账脚本：

```bash
python - <<'EOF'
import json, re, io
d = {r['repo']: r for r in json.load(open('audit_real.json', encoding='utf-8'))}
html = io.open('<手册路径>', encoding='utf-8').read()
for repo, r in d.items():
    exp = {'可执行率': round(r['actionability']*100, 1),
           '闭环率': round(r['closure_rate']*100, 1),
           '保鲜风险': round(r['freshness_ratio']*100)}
    seg = re.search(re.escape(repo) + r'</td>.*?</tr>', html, re.S).group(0)
    for k, v in exp.items():
        assert f'{v}%' in seg, (repo, k, v)
print('对账通过', len(d), '个仓库')
EOF
```

### 第三批 —— 写对账器时撞上的 4 处（比第二批更糟，因为都是校验器自己的问题）

修第二批的方法本身又引出一串问题。这批的共同特征是：**问题不在交付物，
在我用来检查交付物的那个工具里**——而且前两个「能通过」，是我在写完负向测试之后
才发现它们根本没在检查。

1. **对账器第一版是空的。** 它只检查「正确数字有没有出现在 HTML 里」，于是把 KPI
   里的 `1693` 改成 `2199`，它照样报「对账通过」并退出 0。修法：改成按 KPI 卡片
   逐张核「这一格显示的是不是这个值」，并补一条负向测试（注入 2199 必须退 1）。
   **这是第八件 `rc in (0, 2)` 空断言的同族病：能通过的检查等于没检查。**
2. **KPI 正则键值写反。** `findall` 返回 `(数值, 标签)`，第一版直接 `dict()` 了，
   把「数值:标签」建反，怎么查都 `None`；而「没识别到 KPI」的兜底又和输出顺序叠在
   一起，把"压根没解析出来"伪装成"这一格不一致"。修法：`{lbl: val for val, lbl in ...}`。
3. **自检项数硬编码 `36/36`。** 自检从 36 加到 38 之后，对账器里的 36/36 失真，
   报出一堆假不一致。修法：不硬编码，现场跑一遍 `verify.py` 取真实数字。
4. **递归死锁：verify → 对账器 → verify → 对账器**，60 秒超时；而报出来的
   却是「没能解析出自检总数」，把递归问题伪装成一个假的数字不一致。
   修法：加 `LGA_NO_RECURSE` 环境守卫，自举调用不回头再跑 verify。

顺带修掉的：手册残留 `36/36`、CSS 笔误 `#1a2button`、以及一个 `os` 没导入就
用了 `os.environ` 的 `NameError`。

**这批的教训**：第二批我只对了「交付物里的数字」，没对「量数字的工具」。
写完校验器必须喂一次错数据——**它没报错，你就没写检查。**

### 第三批 —— 写对账器时撞上的（这条最打脸）

既然总数字能写错，就写了个 `audit_deliverable.py` 逐格对账。
**但第一版对账器本身是空的**：它只检查「正确数字有没有出现在 HTML 里」，
没有检查「显示出来的数字是不是对的」——

```bash
# 把手册里的 1693 改成 2199，第一版照样报：
对账通过：手册表格与真数据逐格一致      # 退出码 0
```

跟第八件的 `rc in (0, 2)` 是**同一个病**：**能通过的检查等于没检查。**
是**负向测试**（故意注入错值、看它抓不抓得住）把它揪出来的；
再修掉一个键值写反（`dict()` 把「数值:标签」建反了，怎么查都 None），
现在正负双向都对：正例退 0，注入 2199 精确点名「实扫条目应 1693，实际 2199」。

**自检从 36 项加到 38 项**，新增的两项就是这条负向测试。
**纪律**：任何校验器上线前，先喂一次错数据——它没报错，你就没写检查。
